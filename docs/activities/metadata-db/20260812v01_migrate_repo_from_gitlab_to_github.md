## Key Data Decisions and Considerations

1. **Historical docs are dated records and stay as written** — the 16 GitLab-mentioning files under `docs/activities/` and `docs/code_review/` (including `20260529v01_ci_and_gitlab_setup.md`) document what was done at the time; rewriting them would falsify the log. Only living docs (`readme/`), code, and config change.
2. **The revert-on-failure design survives, but the bot identity is the hard part** — GitHub's `GITHUB_TOKEN` cannot push to a protected branch, so the cleanup bot must be a fine-grained PAT or a GitHub App with an explicit branch-protection bypass allowance, mirroring GitLab's Maintainer-role project access token. The auth URL username also differs (`oauth2:` is GitLab-specific; GitHub wants `x-access-token:` for App tokens or the bare token for PATs), which is why the template lives in config and the tests pin its shape.
3. **The loader's SHA seam fails silently if missed** — `db_io.resolve_commit_sha` falls back from the CI-provided variable to `git rev-parse HEAD` with only a warning, so a forgotten `CI_COMMIT_SHA` → `GITHUB_SHA` rename would not break anything visibly; `load_audit` would just record slightly-wrong provenance. Task 8.3 exists to catch exactly this.
4. **`rules: changes:` does not translate 1:1, which drives the two-workflow factoring** — GitHub evaluates `paths:` filters at the trigger, not per job, and the jobs within each pipeline gate on different paths, so both workflows gate per job via a change-detection step instead. The GitLab file documents a hard constraint preserved verbatim: `revert_failed_load` `needs:` the load job, so the two must exist in precisely the same runs — in Actions, the same workflow with `if: failure()` scoped to the load job's outcome.
5. **CODEOWNERS flips from advisory to enforceable** — on GitLab Free the file was documentation-plus-notification; on GitHub it blocks merges wherever "Require review from Code Owners" is on. The sketch handles (`@metadata-db-maintainers`, `@data-ops-team`) must become real org teams before enabling enforcement, or every PR stalls on a reviewer that cannot be requested.
6. **Merge Trains → merge queue** — the readme's Premium-tier recommendation maps to GitHub's merge queue (availability depends on the GHES version, task 7.5); the Free-tier semaphore workaround it documents can be retired in favor of Actions `concurrency` groups on the post-merge workflow.
7. **The ported CODEOWNERS content was already broken, independent of the migration** — its six per-file ocs mapping rules name the retired six-schema layout (`ocs/carr/...` etc.), dead paths since the layout rework (commit 12b08c2); the eleven `puf_*` rules predate `puf` being modelled as one source; `pagila` exists only in the example corpus. The GitHub file is written against the current tree rather than ported, so the migration also functions as the routing-table repair.
8. **The target is GitHub Enterprise Server, not github.com** — `github.example.com` has no GitHub-hosted runners, so Actions being enabled, a registered self-hosted runner, and that runner's network path to Postgres are cutover prerequisites (task 7.5); the readme's "no runner available" manual fallback remains the documented degraded mode. Org/team provisioning and runner infrastructure are prerequisites this activity consumes, not deliverables — their ownership sits with whoever administers the GHES instance.
9. **The revert design requires merge commits, so the repo must allow only the "merge commit" method** — `revert_merge/preconditions.py` identifies the failed merge by git plumbing (exactly two parents) and reverts with `git revert -m 1`, which is only meaningful on a merge commit. The code is platform-neutral and needs no change, but GitHub — unlike GitLab's default — offers squash and rebase merging, and either would make every merge a single-parent commit: the revert job would refuse (`expected 2 parents`) and the GitOps invariant would be unenforceable. Disabling squash/rebase in the repo settings (task 7.4) is therefore part of the migration, not a style preference. If the org later wants squash merges, the revert script needs a redesign (revert the squashed commit itself), which is out of scope here.
10. **(Implementation) The dormancy gate ported as a repository Actions variable** — every job in both workflows carries `if: vars.METADATA_DB_CI_ENABLED == 'true'`, the Actions analogue of the GitLab `workflow:` rule, so the committed workflows stay dormant until the platform setup completes. One semantic difference documented in the workflow header and readme: a skipped job *satisfies* a required status check, so branch protection's required checks (task 7.3) only bite after the variable is set.
11. **(Implementation) Write credentials go in a `metadata-db-write` deployment environment, not plain repository secrets** — an extension of task 1.5 needed to preserve decision-critical semantics: same-repo branch PRs *do* receive repository secrets (only fork PRs are excluded), so a PR editing a workflow file could exfiltrate a plain-secret write credential, breaking the "unreviewed branch code never holds a write credential" invariant that GitLab's protected variables enforced. `load_catalog_data` and `revert_failed_load` declare `environment: metadata-db-write`; creating that environment, restricting it to `main`, and placing `POSTGRES_*` + `CLEANUP_BOT_TOKEN` in it is now part of task 7.2. The RO set stays as plain repository secrets (accepted residual, unchanged).
12. **(Implementation) `remote_url_template` ships filled** — the target URL is fully known (`https://x-access-token:{token}@github.example.com/Warehouse/metadata_db.git`), so unlike the GitLab-era `<group>` placeholder the config sanity check no longer blocks on the URL; `bot_name`/`bot_email` remain `<...>` placeholders the script refuses until an operator fills them (activation checklist). The `x-access-token` username serves both bot options (App installation token; fine-grained PATs also authenticate in the password position).
13. **(Implementation) `.gitlab-ci.yml` and `.gitlab/` deleted in this changeset** — task 1.7's "once green" precondition can only be verified post-cutover (task 8.2's scratch PR), and carrying dead GitLab config into the GitHub repo had no value: the pipeline was dormant-gated on GitLab, and after the cutover no GitLab instance evaluates it. The workflows are dormancy-gated the same way, so nothing runs-and-fails in the interim.
14. **(Implementation) Change detection is `git diff HEAD^1 HEAD`** — on `pull_request` the checkout is the ephemeral PR merge commit, so `HEAD^1` is the current base tip and the diff is exactly the PR's effective change set (also used for the `--allow-pending` / ref-exemption computations); on `push` to main every commit is a single merge commit (or the bot's revert), so first-parent diff is the push's change set. Consequences wired into the workflows: `fetch-depth: 2` (or `0` where scripts diff history), and git is installed in the `python:3.14-slim` container *before* checkout — without git, actions/checkout silently falls back to a tarball download with no `.git` directory, which would break every diff, the loader's SHA fallback, and the revert itself.
15. **Task 8.1 ran here: `python -m pytest code/ -q` → 1118 passed, 19 skipped, 2 pre-existing errors** — the two errors are `code/bootstrap/generate_ocs_corpus/unit_tests/test_generate_ocs_edw_mappings.py` fixtures that read the real `data_catalog/sources/ocs` tree, which is mid-rework in this working copy (the staged `ocs` → `ocs_old` rename); unrelated to this migration and untouched by it. All revert_merge (55) and db_io (86) tests pass with the renamed fixtures.
16. **Tasks 7 and 8.2–8.3 are blocked on platform access** — they are settings on `https://github.example.com/Warehouse/metadata_db` (repo creation/push, secrets + the task-11 environment, branch protection with the bot bypass, merge-method restriction, GHES admin confirmations) and live post-cutover runs; nothing further can be done from the repo working tree. They stay `[pending]` for whoever holds GHES access.
