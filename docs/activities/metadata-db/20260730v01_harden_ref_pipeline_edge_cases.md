## Implementation Plan

### Phase 1 — Loader guards, escape hatches, and data_ref structure

1. [completed] Harden validation, complete the exemption family, and add the schema-folder structure - `code/load_ref_data/load_ref_data.py`
   - 1.1. PK guard: a table with no primary key (live introspection returns none, or — on the docs-shape path — no documented column has `is_primary_key: true`) is a validation issue, not a silent skip of duplicate detection; a curated code set without a PK is always a mistake
   - 1.2. Docs-shape validation: replace the shallow docs-only checks with full validation against the documented shape — header equals the documented columns, values parse per documented `data_type`, empty cells only on documented `is_nullable: true` columns, PK uniqueness over the documented key columns — so a table the live DB cannot vouch for is validated as strictly as one it can
   - 1.2b. Documented `data_type` becomes a machine contract on the docs-shape path: a documented type outside the loader's parser vocabulary raises an explicit issue naming the column, the offending value, and the allowed vocabulary (ref docs must use parseable type names, unlike the freeform `data_type` prose elsewhere in the corpus)
   - 1.3. `--allow-missing-table` (new-table MRs) uses the docs-shape validation from 1.2 instead of the current shallow checks
   - 1.4. New repeatable `--allow-reshaped-table <name>` (dry-run only, rejected otherwise like `--allow-missing-table`): the named existing table validates against the docs shape instead of the live columns — the escape for an MR that alters a ref table's columns, whose migration applies post-merge
   - 1.5. New repeatable `--allow-dropped-table <name>` (dry-run only): the named table's DB-table-without-CSV bidirectional-drift issue downgrades to a warning — the escape for an MR that retires a ref table, whose drop migration applies post-merge
   - 1.6. Duplicate-doc diagnostics: the docs gate detects duplicate documented column names and names the duplicated columns and the offending files, instead of the current list-vs-set mismatch that reports `undocumented: [], documented but absent: []`; `documented_columns` deduplicates shard files by resolved path so a shard literally named `columns/columns.yaml` is read once, not twice
   - 1.7. Wrap `check_freshness`'s CSV byte read so any `OSError` (not just `FileNotFoundError`) surfaces as the documented `ValueError` contract, matching `read_csv`
   - 1.8. Schema-folder discovery: CSVs live at exactly `data_ref/<documented_schema>/<table>.csv` — discovery walks the schema folders; a CSV directly under `data_ref/` or nested deeper than one folder is an error, and a folder name that does not match a documented schema of the ref source (a schema folder under `docs_dir`) is an error naming the valid schema folders
   - 1.9. Global stem uniqueness: two CSVs with the same stem in different schema folders is a hard error naming both paths (one physical namespace underneath — last-one-wins is never acceptable)
   - 1.10. Drift-message paths: the bidirectional-drift and docs-gate messages that spell CSV paths (`data_ref/<table>.csv`) update to the schema-folder form (`data_ref/<schema>/<table>.csv`)

## Key Data Decisions and Considerations

1. **Docs-shape validation is the unifying mechanism** — The ref docs already author `data_type`, `is_nullable`, and `is_primary_key` per column, so validating against the documented shape gives new-table and reshaped-table MRs nearly the same strictness as live-table validation (everything except live introspection itself). This replaces the shallow docs-only path rather than adding a third validation tier, and it is what makes the reshape escape safe to offer: the docs gate remains fully enforced, so an exempted table is never validated against nothing.
2. **CI computes every exemption from the MR's own diff** — Same principle as `check_schema_in_sync --allow-pending` and the existing `--allow-missing-table` computation: added CSVs → missing, deleted CSVs → dropped, modified CSVs → reshaped (the last only when the MR touches `ddl_ref/`, so value-edit MRs keep full live strictness). Authors cannot exempt arbitrary tables, and `--no-renames` closes the hole where git's rename detection (default on since git 2.9) hides a renamed CSV from `--diff-filter=A`.
3. **All exemption flags are dry-run only** — A real load or `--check` must never skip a drift or missing-table error; the flags exist solely for the pre-merge window where the DB legitimately lags the MR. This extends the existing `--allow-missing-table` stance unchanged.
4. **The PK guard is two layers deliberately** — The static DDL test catches a PK-less migration at review time; the loader issue catches a PK-less live table however it arose (e.g. a hand-applied hotfix). Both are one-liners and the failure mode they prevent — silently loading duplicate codes into a curated set — defeats the purpose of ref.
5. **Escape hatches over pre-merge DDL application** — The alternative fix for drop/reshape MRs is blessing maintainer application of unmerged-branch migrations pre-merge. Rejected: it inverts the apply-what-main-holds discipline, and the exemption approach keeps the whole flow reviewable in one MR with no out-of-band ordering.
6. **Deliberately not fixed** — Docs column order vs CSV order stays unchecked (authoring freedom; an ordered docs gate would force docs churn on every reshape); the loader's config knobs (`csv_dir`, `docs_dir`, log dirs) stay cwd-relative (run-from-repo-root is the operational convention; the 968ab41 vendoring made only imports cwd-independent, which is the part CI needed); the CI word-splitting of accumulated flags stays (stems are constrained `[a-z0-9_]`); the int/float parser-parity edges stay per activity 20260729v03 decision #9. Recorded so the next review does not re-litigate them.
7. **Audit provenance** — Every finding here was empirically reproduced on 2026-07-30 against 968ab41 (PK-less duplicate rows return no issues; duplicate doc rows report empty diagnostic lists; a `columns/columns.yaml` shard double-counts; git 2.53 confirms rename detection defaults on). The drop/reshape gaps falsify activity 20260729v03 decision #9's claim that the new-table case was "the only false-failure case" of validating against live DDL.
8. **Dependencies and ordering** — Task 2 depends on Task 1; Task 4 depends on Task 1's flags existing (the CI change must not merge first or MR pipelines would pass unknown flags); Task 7 depends on Task 1.8 (the loader must accept schema folders before the CSV moves) and Task 6.1 (the deployments value must match the config the loaders use); Task 8 describes Task 1/4/6/7 behavior so it lands with or after them; Task 9 requires everything and is the gate that verifies the rename end to end. Tasks 3 and 5 are independent. Single-MR landing is fine; if split, Phases 1-5 (code + CI + rename) then Phases 6-7 (docs + rebuild).

10. **Rename scope: physical schema only** — Maintainer direction (2026-07-30). The Postgres schema becomes `metadata_db.reference` (clearer for anyone connecting to the DB); the folder/loader family (`data_ref/`, `load_ref_data`, `ddl_ref/`, `grant_ref_ro.sql`, `apply_ddl_ref.toml`, CI job names) keeps `ref` as its shorthand, and every catalog id (`ref.codes.*`, the 118 `ref_table` links) is untouched. The documented schema folder stays `codes`: it is a content label, the physical name lives solely in the deployments schemas map, and renaming it would churn all links for the redundant `ref.reference.*` id shape.
11. **data_ref structure is enforced at the schema level only** — Exactly `data_ref/<documented_schema>/<table>.csv`, strict (no top-level CSVs, no deeper nesting, folder must name a documented schema). This makes the folder level semantic (self-describing tree; anchors a future where different documented schemas target different physical schemas) while staying well-defined. Mirroring the docs *shard* level was considered and rejected: shards are freeform many-tables-per-file groupings, CSVs are one-per-table, so a mirror is ill-defined and would couple cosmetic docs reorganizations to CSV moves. Stems stay globally unique across folders (one physical namespace; the loader errors on collision, and the deployment physical-address UNIQUE backstops it in the DB).
12. **Multi-category future left open** — A future reference category (e.g. crosswalks) can be a sibling documented schema mapping N:1 onto the physical `reference` schema via the deployments map (its `schema.yaml` description must state the partition is logical, since Postgres sees one schema), or can get its own physical schema via migration (1:1 again, but needs loader multi-schema support — which the schema-folder convention from decision 11 anchors). Neither is decided now; both stay cheap.
13. **The full rebuild replaces all migration ceremony** — Maintainer direction (2026-07-30): both schemas are dropped and re-applied, so the rename needs no `ALTER SCHEMA` and no new migration (the DDL is schema-agnostic; the configs are the schema's identity). Task 6.2's comment-only edits to `ddl_ref/0001` (its header names the physical schema) change that file's checksum and ride the rebuild's bootstrap exception — the fresh `ddl_versions` records the new checksum, exactly as in activity 20260729v03; `ddl_catalog/0001` needs no edit (its `ref` mentions are the catalog source label, which stays). The docs shard split and CSV move are content-neutral; the only row-level change is the deployments physical-schema value, and since every row is a fresh insert on rebuild, no `update_reason` is needed anywhere.
