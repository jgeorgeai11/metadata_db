## Implementation Plan

1. [completed] Schema name is interpolated raw into the libpq connection options — `code/apply_ddl/apply_ddl.py`
   - 1.1. [suggestion] Line 102: `connection_kwargs` builds `options=f"-c search_path={schema}"` by string-formatting the schema straight from config. Everywhere else the same schema value is passed through `psycopg2.sql.Identifier` (line 157, `ensure_schema`) precisely to avoid concatenating an identifier into statement text. In the libpq options string, spaces separate individual `-c` options, so a schema name containing a space (or other special characters) would silently break `search_path` or smuggle in extra options. The value comes from trusted TOML config, so this is robustness/consistency rather than an active injection path — but a cheap up-front validation would make the failure loud instead of silent and keep the identifier-handling consistent with the rest of the module.
        - Current: `"options": f"-c search_path={schema}",`
        - Expected: validate `schema` against an identifier pattern before use (e.g. `if not re.fullmatch(r"[A-Za-z_][A-Za-z0-9_]*", schema): raise ValueError(f"Invalid schema name: {schema!r}")`) and then interpolate, so a malformed schema fails fast with a clear message.
        - Resolution: Implemented as specified. Added a module-level `SCHEMA_NAME_RE = re.compile(r"[A-Za-z_][A-Za-z0-9_]*")` (with a comment explaining the libpq-options risk) and a `if not SCHEMA_NAME_RE.fullmatch(schema): raise ValueError(f"Invalid schema name: {schema!r}")` guard at the top of `connection_kwargs`, before `load_dotenv()`. Documented the new `ValueError` in both `connection_kwargs`'s and `run`'s `Raises` sections; the `ValueError` propagates to `main`'s existing `(FileNotFoundError, ValueError, RuntimeError)` handler. All 51 unit tests still pass (existing tests use valid schema names).

2. [completed] Inconsistent error-message context in `main`'s exception handlers — `code/apply_ddl/apply_ddl.py`
   - 2.1. [minor] Line 502: The `(FileNotFoundError, ValueError, RuntimeError)` handler logs the bare exception with `logger.error(f"{e}")`, while the sibling handlers prefix a category for context — `logger.error(f"Missing required config field: {e}")` (line 498) and `logger.error(f"Database error: {e}")` (line 506). Logging guideline 3 (include context). These exceptions already carry descriptive messages, so this is a consistency nit rather than a loss of information; adding a short prefix would make the log line self-describing and symmetric with the other arms.
        - Current: `logger.error(f"{e}")`
        - Expected: `logger.error(f"Error: {e}")` (or a more specific category prefix consistent with the other handlers).
        - Resolution: Implemented as specified — changed line 502 to `logger.error(f"Error: {e}")`. A single `Error:` prefix was chosen over a more specific category because the arm handles three distinct exception types (`FileNotFoundError`, `ValueError`, `RuntimeError`); the exceptions themselves already carry descriptive messages, so the generic prefix keeps the log line self-describing and symmetric with the sibling handlers without overclaiming a category.
